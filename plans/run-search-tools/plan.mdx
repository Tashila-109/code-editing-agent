# run_command and search_files tools

This repo is a minimal code-editing agent: a CLI chat loop (all in `main.go`, package `main`) that gives a Claude model three tools — `read_file`, `list_files`, `edit_file`. The model currently works blind: it cannot run the code it edits or search file contents. This plan adds two tools. `run_command` executes a model-chosen shell command via `sh -c`, but only after the human approves it at an interactive `Allow? [y/N]` prompt that fails closed (non-TTY stdin, EOF, empty, or garbage all decline); output is capped at 10KB, a 30s timeout kills runaways, and the exit code is always reported. `search_files` runs a Go RE2 regex over file contents under an optional path, skipping `.git` and binary files, returning up to 100 `path:line: text` matches.

**Done means:** both tools exist in their own files with table-driven tests (the repo's first tests), `main.go`'s `tools` slice lists five definitions, and the full gate passes — `gofmt -l .` clean, `go build ./...`, `go vet ./...`, `go test ./...` (final gate adds `-race` and the `go run . < /dev/null` smoke run).

Source documents in this repo: the approved design at `docs/design/run-search-tools/design.md` (all INV-n / AC-n IDs below are defined there) and the approved task breakdown at `docs/planning/run-search-tools/plan.md`. Branch: `feat/run-search-tools`. Every product decision (sh -c, y/N gate, caps, timeout, RE2 walk) is settled in the design — this plan has no open questions.

## Stage lanes

Two stages. Stage 1's tasks run in parallel: their file sets are disjoint (each creates only its own tool file and test file) and both consume only symbols that already exist in `main.go` — neither consumes anything the other defines. Stage 2 starts only after both stage-1 tasks are committed.

<Callout id="registration-split-decision" tone="decision">

The `main.go` registration edit is pulled out into its own stage-2 task. Folding registration into each tool task would give both stage-1 tasks a shared file and serialize the whole feature over a one-line edit; splitting it keeps stage 1 parallel-safe, and the stage-2 task still owns a checked outcome (AC-14 plus the smoke run).

</Callout>

## Stage 1 — the two tools, side by side

<Columns id="stage1-tasks">
<Column id="stage1-run-command" label="Task: run_command (gate + exec)">

<RichText id="stage1-run-command-body">

**Files:** `run_command.go`, `run_command_test.go` (both new)

Delivers the `run_command` tool complete and tested at package level: the model supplies a command, the human sees it verbatim and answers `y`/`yes` to run it via `sh -c` with a 30s timeout (`WaitDelay` 2s) and a 10240-byte combined-output cap.

Decided constraints (design Sections 3, 5–7):

- The gate reads stdin **one byte at a time** through the first newline — never a `bufio` reader, because the chat loop already owns a `bufio.Scanner` on `os.Stdin` and a second buffered reader would swallow the user's next chat message.
- Non-TTY stdin (char-device check) declines *before* prompting; EOF, empty, and garbage answers decline. Fail closed, per-invocation approval, no "always allow".
- Decline and "sh could not start" return Go errors (becoming error tool results); a non-zero exit is a **normal** result with `exit code: <n>` and output.
- Exact error strings, result format, and the test seams (`confirmIn`, `confirmOut`, `commandTimeout`, `stdinIsTerminal`) are fixed by the design.

**Proof:** INV-1…INV-5, INV-9, half of INV-8; AC-1…AC-8, AC-15 — table-driven tests swap the seams and use a `t.TempDir()` sentinel file to prove declined commands never start.

</RichText>

</Column>

<Column id="stage1-search-files" label="Task: search_files (regex walk)">

<RichText id="stage1-search-files-body">

**Files:** `search_files.go`, `search_files_test.go` (both new)

Delivers the `search_files` tool complete and tested at package level: a Go RE2 pattern matched against every line of every text file under an optional relative path (default `.`), returning `path:line: text` matches.

Decided constraints (design Sections 3, 5–7):

- Pure Go stdlib — no shelling out to grep, no path sandboxing (deliberately consistent with `read_file`/`list_files`).
- Whole-file read with `os.ReadFile`, split on newline (sidesteps the 64KB `bufio.Scanner` line limit); a NUL byte in the first 8KB marks a file binary and it is skipped; `.git` is never entered.
- Caps: 100 matches (walk stops via `fs.SkipAll`, truncation note appended), 250 bytes per emitted line.
- Errors only for an invalid regex or an unreadable root; unreadable entries mid-walk are skipped silently and the search continues.

**Proof:** INV-6, INV-7, half of INV-8; AC-9…AC-13 — `t.TempDir()` fixtures: plain match, nested dir, `.git/config` match, NUL-file match, 150-match file.

</RichText>

</Column>

## Stage 2 — register both tools

After stage 1 both tools exist and pass their tests, but the agent never offers them to the model. Stage 2 makes the single permitted `main.go` change — the `tools` slice in `main()` grows from three definitions to five. No other edit: no refactors, no touching the chat loop or existing tools.

## Verification

Every task runs the repo's standard gate before its commit; verbatim output is the evidence.

```sh
gofmt -l .              # must print nothing
go build ./...
go vet ./...
go test ./...
```

The final gate (testing stage, after stage 2) adds:

```sh
go test -race ./...
go run . < /dev/null    # prints the banner, exits 0 — live fail-closed smoke
```

The run_command tests execute real `sh` — that is the unit under test; dev and CI are darwin/linux (Windows is out of scope).

<Callout id="accepted-ceilings" tone="risk">

Accepted ceilings, decided in the design and not to be "fixed" during implementation: an answer typed **before** the prompt appears strands in the chat scanner's buffer (the visible prompt blocks until re-answered — recoverable, no data loss); background grandchildren of a timed-out compound command may survive as orphans (`WaitDelay` guarantees the tool returns; process-group kill is the recorded upgrade path); scripted piped-stdin sessions can never approve a command — that is the point of the human gate.

</Callout>
